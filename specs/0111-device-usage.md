# 0111 — Device usage odometer and classification

## Purpose

Per-device monthly data usage, brand identification, and device form factor
classification.

The Starlink router resets per-client byte counters (`rxStats.bytes`,
`txStats.bytes`) on every Wi-Fi re-association, and keeps no historical log.
The odometer polls the router's client counters, accumulates valid deltas,
treats legitimate counter drops as Wi-Fi resets, skips unobserved time gaps,
and tracks monthly usage keyed by the router's stable `clientId`.

Additionally, the MAC address OUI is resolved against the IEEE registry,
private/randomized MACs are identified, and device names are classified into
human-friendly device kinds (`phone`, `laptop`, `tv`, `console`, etc.) for
native icons and labels.

## Requirements

- **SPEC-DEV-001** — The MAC address is resolved against the IEEE OUI registry
  (`crates/dishy-core/data/oui.json`). Randomized / locally-administered MAC addresses
  (second hex character `2`, `6`, `a`, or `e` case-insensitive) are identified
  as private and never mapped to a real vendor brand.
- **SPEC-DEV-002** — A device is classified into `DeviceKind` (`phone`,
  `laptop`, `desktop`, `tablet`, `watch`, `tv`, `console`, `light`, `unknown`)
  using token matching and distinctive substring rules on the display name,
  matching the TypeScript reference implementation.
- **SPEC-ODO-001** — Each device's odometer state is keyed by the router's
  `clientId`, falling back to the MAC address only when `clientId` is absent.
  Cumulative lifetime bytes are tracked across reconnects.
- **SPEC-ODO-002** — Counter increments (`counter >= prev`) add the delta
  (`counter - prev`). Counter drops (`counter < prev`) within the 2.5 Gbps link
  ceiling (`elapsed_ms * 312_500` bytes) represent Wi-Fi re-association resets
  and are added whole; drops exceeding the ceiling are ignored. Gaps exceeding
  15 seconds re-baseline without adding traffic.
- **SPEC-ODO-003** — Usage is bucketed by local calendar month (`year * 12 + month`).
  The first reading in a new month files the completed month into history
  (retaining up to 6 months) and re-anchors the running month to zero.
- **SPEC-ODO-004** — An unknown `clientId` adopts an orphaned bucket if its MAC
  is unique to that single orphan and the MAC has never been flagged as shared.
  A masked MAC observed carrying two or more concurrent devices is permanently
  recorded as shared and never adopted.
- **SPEC-ODO-005** — The odometer state is saved to `client-totals.json` via
  atomic temporary file rename, matching schema version 4.
- **SPEC-ODO-006** — The Data Usage page displays the per-device usage list
  sorted by total bytes descending, showing device icon, resolved name,
  subparts (vendor, stale month, active now / relative time), total bytes, and
  directional down/up bytes. Per-device reset, per-device removal, and month
  clearing are supported. Viewing the page activates client roster polling.
- **SPEC-ODO-007** — A roster entry missing either byte counter is not a
  counter reading: it does not change the baseline, total, name, IP address, or
  last-seen time. Missing data must never be treated as a reset to zero.
- **SPEC-ODO-008** — Each valid reading refreshes the saved display name and IP
  address when present, while an absent or empty value leaves the last known
  value intact.
- **SPEC-ODO-009** — A schema version 3 snapshot is migrated to version 4,
  preserving its current-month totals, month, shared MAC evidence, aliases, and
  rejected identity pairs.
- **SPEC-ODO-010** — Only roster entries with no role or the `CLIENT` role feed
  the odometer. Saved display names prefer the router's given name over its
  hostname.

## Acceptance criteria

- Conformance contract tests verify odometer arithmetic, reset handling,
  gap skipping, month roll, adoption, and shared MAC logic against golden
  outputs generated by the TypeScript reference implementation.
- Unit tests verify OUI vendor lookup and device classification against golden
  fixtures.
- GTK tests verify row rendering, sorting, clear-all confirmation, and action
  dispatch through the recorder channel.
- `cargo fmt --check`, `cargo clippy -- -D warnings`, and `spec_traceability`
  pass.
