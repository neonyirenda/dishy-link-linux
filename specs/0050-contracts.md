# 0050 — Contract corpus

## Purpose

The Rust port must match the TypeScript implementation's behaviour, not merely
compile. The corpus is the mechanism: captured wire bytes and their expected
decoded form, generated from the TS side and consumed by both test suites.

## Requirements

- **SPEC-CONTRACT-001** — Each captured response frame decodes, through the
  bundled schema, to exactly the golden JSON committed beside it. Numeric
  comparison follows the single-precision tolerance defined in spec 0020.
- **SPEC-CONTRACT-002** — Request frames generated by the TypeScript exporter
  are byte-identical to the frames the Rust client builds.

## Generation

```
node_modules/.bin/tsx scripts/export-contracts.mts
```

The exporter reads `schema/dish.protoset` and `schema/sample-*.json`, then
writes:

```
contracts/grpc/*.request.bin
contracts/grpc/*.response.bin
contracts/golden/*.json
```

Fixtures are committed so `cargo test` needs no Node install. A stale corpus is
a contract failure, not a tooling failure.

## What belongs in the corpus

- One response per RPC the app reads.
- Requests whose encoding is non-obvious (oneof selections, config writes,
  stow/unstow).
- Cross-language maths: latency buckets, energy buckets, alert transitions.
- No credentials, no account identifiers, no live session cookie.
